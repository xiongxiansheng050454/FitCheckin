# IronPlan implementation contract

Sharing extension: `packages/share/poster/index` generates a 750x1320 PNG from the local frozen daily record or the selected month's completed actions. Daily generation requires all current-day actions completed; monthly generation requires at least one training day, including cardio-only days. Posters emphasize capacity with a dark header and large bold lime number, offer five selectable captions, and include one IronPlan brand, cardio totals, and an enlarged official release mini program code. Estimate labels appear in the footer. Monthly posters also include the calendar and a colorful donut covering all muscle groups with nonzero volume. Pending local data is labeled. Images are generated on-device and are only saved/shared through explicit user commands. Cloud `posterCode` requires native OPENID/AppID and returns `{code:0,data:{base64,mimeType}}` or `POSTER_CODE_ERROR` without backend details. No database migration is required.

Approved scope: native WeChat personal fitness app, finite multiweek cycles arranged from weekly templates with week overrides, sequential set confirmation, native rest countdown, today-only edits, monthly estimated volume, application/user-isolated document database, durable offline queue. Main/each subpackage <=2MB, combined <=30MB; budgets 1.5MB each/6MB total. No social feed or historical editing. On 2026-10-05 the user changed the backend from PostgreSQL to document database, added per-set training and replaced infinite weekly repetition with dated cycles. See [training acceptance](training-testing.md) and [cycle contract/acceptance](cycles-testing.md).

Cycle extension: state adds `program:null|{id:'program',from,cycles:[]}` and `cyclesSupported`. One versioned program entity serializes all cycle arrangements and detects competing schedules. `saveCycle(cycle,expectedRevision?)` and `deleteCycle(id,expectedRevision?)` use the existing queue. `packages/manage/cycle-edit/index?id=...` edits dated week sequences; query `template` preselects a weekly template. A cycle stores `{id,name,startWeek,plans:[{id,templateId,name,days}],weeks:[snapshotId]}`. Repeated weeks share an immutable snapshot within the cycle. `resolveDay` preserves record precedence, then resolves the dated cycle and matching override, then legacy repetition before `program.from`. Beyond the final cycle there is no plan. `scheduledWeek`, `cycleStatus`, `cycleEnd`, `shiftDate` support scheduling UI. Overrides optionally add both `cycleId` and `planId`. Effective schedule history uses a zero fallback mask plus explicit dated week masks, preserving past continuity without repeating after expiration. Bootstrap/pull advertise `cyclesSupported:true`; the generic document backend validates the new program kind and protects past week snapshots in the same transaction.

Completion feedback: Today automatically celebrates only a local incomplete-to-complete transition, at most once per owner/date on this device, and vibrates without waiting for the network. The shared main-package poster component prepares in the background and opens a same-page overlay. Shared model/render/runtime modules live under `lib`; subpackage wrappers remain compatible. Images use `wx.showShareImageMenu`; older clients share mini program cards through `open-type="share"` and `onShareAppMessage`.

Optional `scheduleHistory`: ascending `[{from:'YYYY-MM-DD',mask:0..127,weeks:[{week:MondayDate,mask:0..127}]}]`. Before finite cycles this is on the profile; after migration it is stored atomically with the program, inheriting existing profile history. Mask bit 0 is Monday. Current-day edits replace today's event, preserve older events, and enter the same local persistent batch as the originating mutation. Bootstrap/pull add `scheduleHistorySupported:true` after the compatible backend update; the client gates new history writes on that capability. Continuity uses saved schedules for missing record dates, skips rest days, counts days with at least one completed set and breaks on a past scheduled day with no completed sets. Older missing schedules are explicitly estimated from the current plan. Monthly population rankings are not implemented; encouragement compares real personal prior-week records.

Cycle-template extension: `cycleTemplate` entities store `{id,name,weeks:[weeklyTemplateId]}` with 1-52 ordered weeks. State includes `cycleTemplates:[]` and persisted `cycleTemplatesSupported`; bootstrap/pull advertise the capability after deployment. Store exposes `saveCycleTemplate(body,expectedRevision?)` and `deleteCycleTemplate(id,expectedRevision?)` with the existing queue, ownership and conflict handling. Referenced weekly templates cannot be deleted locally until removed from cycle templates. Remote missing references are visible and repairable. `cycleFromTemplate(state,template,startWeek)` resolves latest weekly parameters into deduplicated independent snapshots; later template changes leave arranged cycles unchanged. Editor query `mode=template&id=...` edits reusable sequences without dates; `cycleTemplate=...` schedules the entire sequence after the last cycle. Dated cycles can be saved as reusable templates. No new collections or indexes are needed.

## Shared domain (miniprogram/lib/domain.js)

Exports: `MUSCLES` [{id,name}], `PRESETS` [exercise], `today(now?)`, `weekStart(date)`, `monthOf(date)`, `shiftMonth(month,delta)`, `monthDates(month)`, `weekday(date)` (0=Monday), `newId(prefix)`, `validateExercise(exercise)`, `exerciseSummary(exercise)`, `resolveDay(state,date)`, `calculateRecord(record)`, `calculateMonth(records,month)`, `defaultMuscleWeights(primary,secondary)`.

Exercise: `{id,name,type:'weighted'|'bodyweight'|'cardio',sets,reps,weight,coefficient,restSeconds,durationMinutes,distanceKm,intensity,muscles:[{id,percent}]}`. Numerical fields are numbers; weighted/bodyweight have reps; cardio duration/distance are per set. Template: `{id,name,days:[[],[],[],[],[],[],[]]}` (7 arrays of exercise snapshots, each adds stable `entryId`). Override: `{id:weekStart,templateId,days}`. Profile: `{id:'profile',bodyWeight:null|number,activeTemplateId:null|string}`. Record: `{id:date,date,templateId,bodyWeight,items:[exercise plus entryId],completed:[entryId],completedSets?:{[entryId]:integer},startedAt:ISO}`. Full day snapshot freezes on starting the first action, including bodyweight. Starting earns no volume or training day. Records retain their snapshot after all sets are undone. Absent `completedSets` denotes legacy action-level completion: each completed action contributes all its sets. Present `completedSets` is authoritative; `completed` must equal the IDs whose counts reach planned sets.

`resolveDay(state,date)` returns `{templateId,items,isOverride,hasPlan}`; existing record wins, then matching override, then active template. `calculateRecord` returns `{volume,weightedVolume,bodyweightVolume,cardioMinutes,cardioKm,cardioCount,completedCount,totalCount,completedSetCount,totalSetCount,muscles:{[id]:volume},status:'none'|'partial'|'complete'}`. Volume and cardio duration/distance use confirmed set counts. `cardioCount` counts cardio exercises with at least one confirmed set, regardless of sets. `calculateMonth` aggregates capacity, cardio and completed actions plus `{trainingDays,days:[{date,...recordTotals}],muscles:[{id,name,volume,percent}],records}`; days includes every calendar date. `completedSets(record,item)` handles both record versions; `recordSnapshot(record)` omits both mutable completion fields.

## UI store (miniprogram/lib/store.js)

Gym/RPE extension: exercise adds optional `rpe:null|number`; both domain and backend require finite values within 0–10 for weighted/bodyweight and 6–20 for cardio. Absence/null preserves legacy compatibility. Existing `intensity` and `distanceKm` fields remain readable and valid for old snapshots; new editor saves clear free-text intensity/distance, cardio reps and weight. RPE has precedence in summaries and per-set labels, including zero. Preset `run` keeps its ID and becomes 跑步机; strength presets store weight 0 (unset) and show 重量待填写 rather than prescribing a load. User weight remains editable and drives capacity. New presets use adjustable RPE 8 (strength) /12 (cardio). Editor initializes missing RPE only in the unsaved draft and resets it on switching between distinct cardio/strength scales. Native slider and adjacent accessible gray circled question mark provide RIR/Borg descriptions; descriptions are subjective targets, not population comparisons. Distance is removed from all product views/posters while legacy totals remain available internally. App is scoped to gym training without outdoor/watch integration.

Singleton export: `init() Promise`, `getState()`, `subscribe(fn) -> unsubscribe`, `refresh() Promise`, `retrySync() Promise`, `saveProfile(body)`, `saveExercise(body)`, `deleteExercise(id)`, `saveTemplate(body)`, `deleteTemplate(id)`, `activateTemplate(id)`, `saveOverride(body)`, `deleteOverride(weekStart)`, `startToday(entryId)`, `completeTodaySet(entryId,zeroBasedIndex)`, `undoTodaySet(entryId,zeroBasedIndex)`, `resolveConflict(conflictId,'cloud'|'local')`. `toggleToday` remains for compatibility, while Today uses only set operations. Starting and set writes require the persisted `setProgressSupported:true` bootstrap/pull capability; missing capability reports `SERVER_UPDATE_REQUIRED` before enqueueing. Set confirmation accepts only the next index; undo accepts only the last confirmed index.

Today persists `{date,activeId,rest:{entryId,afterSet,duration,endAt,notified,away}|null}` under `ironplan:training:<environment/account key>`. Rest starts after confirmed non-final sets with positive intervals; zero intervals proceed directly. A timestamp drives the display, not accumulated timer ticks. Hide clears timers and screen wake, marks `away`; show recalculates and resumes while positive, or presents expired encouragement and vibrates once. Sessions reset at Beijing midnight/account changes and discard rest when the cloud count or frozen action no longer matches. Rest is local to the device, while set counts synchronize through the existing queue. No per-tick storage or network requests are made.

All mutation functions return Promise, persist locally before network, and reject validation errors with readable Chinese `message` and `code`. State: `{profile,exercises:[],templates:[],overrides:[],records:[],revisions:{'kind:id':number},identityReady,loading,sync:{status:'idle'|'syncing'|'pending'|'error'|'conflict',pendingCount,message,conflicts:[]}}`. Save methods accept optional `expectedRevision` as second argument, rejecting `STALE_DRAFT` when editor's captured baseline differs from current state. UI may render cached state before identity confirmation but cannot mutate until `identityReady`; first-ever offline use cannot invent a user identity. Domain `resolveDay` consumes this state. Conflicts include `{id,kind,entityId,local,cloud}`.

Page routes: main `pages/today/index`, `pages/plans/index`, `pages/stats/index`; management `packages/manage/plan-edit/index`, `packages/manage/exercise-picker/index`, `packages/manage/exercise-edit/index`, `packages/manage/settings/index`; history `packages/history/day/index?date=YYYY-MM-DD`. Plan editor query `id` for existing template; `week=YYYY-MM-DD` for override; picker returns selected exercise using eventChannel `exerciseSelected`. Exercise editor may accept `id` or preset id; picker custom action refreshes on return. UI must use only this store and domain API; no direct database/cloud calls.

## Cloud contract

Weight onboarding: Today waits for foreground, confirmed identity and completed initial loading before showing a native input overlay when profile weight is missing. Existing weight suppresses it. Save validates a positive finite weight ≤500kg, writes only profile weight with the captured revision through the durable store, and reminds users to edit under 我的. Skip/save acknowledgement is persisted per environment/account at `ironplan:weight-onboarding:<store.accountKey()>`; no public weight sharing is implied. Local drafts and markers are isolated from other accounts; stale revisions show an inline error, and an old account's completion cannot dismiss or mark a new account's prompt. Rest/poster/celebration defer onboarding. The top-right 我的 entry reuses secondary small-button styling; settings navigation/header is 我的. No backend/schema change is needed.

Function `fitcheckin`: `bootstrap` -> `{code:0,data:{openid,entities:[...]}}`; `pull` -> same entities; `mutate` with `operation` -> `{code:0,data:{entity}}` or `{code:'CONFLICT',message,data:{entity}}`. Entity `{kind:'profile'|'exercise'|'template'|'override'|'record',id,body,revision,deleted:false|true}`. Operation `{operationId,kind,id,body,deleted,baseRevision,occurredAt:ISO}`. Only native `cloud.getWXContext().APPID/OPENID` authorizes requests; reject missing identity and wrong APPID. Env `weixing2-d7g2j6asyc5132905`; appid `wxe25930a2cdce35d0`. Document collections `fitcheckin_entities` and `fitcheckin_operations`, hashed application/user/entity IDs, optimistic revisions, tombstones, transactionally committed operation receipts and entity changes. Client database reads/writes are denied; runtime credentials permit backend access without a server API Key. Pull uses an appId/ownerId/sortKey compound index and keyset pagination. Client caches and pending operations are isolated by environment and OPENID; previous environment data is retained without automatic migration. Shared instance billing and additional AppID associations are console configuration, not code configuration.

Record mutation may update only `completed` and optional `completedSets` after creation; snapshot fields remain immutable. Server validates set count keys, bounded integer counts and exact consistency with completed action IDs. Initial record date and operation occurrence date must be same Beijing day, cannot be future. Past network submission of already persisted day operations is accepted, while UI prevents new historical operations. Validate all nested exercise fields, seven template days, muscle total 100 and bounded payloads on server too. Backend never computes monthly totals from untrusted client aggregates.

Cloud entity kinds additionally include `program` and `cycleTemplate`; unknown kinds are rejected. The same transaction validates and versions reusable templates, including bounded names, week counts, IDs and payloads.

## Validation

Supersets: exercise `type:superset` stores 2–10 non-nested `components`, with shared `sets`/`restSeconds` and empty outer `muscles`. Each component is an independent normal exercise snapshot with `sets:1`/`restSeconds:0`, its own repetitions or duration, load/coefficient, RPE and muscle distribution. The editor selects copied library actions and edits their private parameters; editing a plan uses the same event-channel contract. Runtime treats the container as a single action and confirms/undoes one full set; no component progress counters or guided transitions are introduced. Capacity/muscle/cardio sums use the outer confirmed-set count for each component, with only the container contributing to total set/action counts. Selfweight prerequisites apply to nested components. Snapshots remain protected by existing immutability and explicit Today-update checks. Backend `supersetsSupported` is persisted per account, with a write gate until the new backend has been confirmed; existing document collections are reused.

Explicit current-day plan update: `todayPlanUpdate(state,date)` builds a candidate from the latest schedule, preserving parameters/counts for any action with confirmed sets and retaining those actions even if removed from the schedule. Zero-progress actions can be replaced; new actions start at zero. `store.updateTodayPlan(expectedRevision?)` is gated by persisted `todayPlanUpdateSupported`, validates only today's candidate and writes an operation with optional `updatePlan:true`. Ordinary record mutations remain immutable. The document transaction allows the explicit operation only on an existing record, with unchanged date/origin/start metadata, unchanged existing non-null bodyweight, preserved performed-action snapshots and exactly preserved counts; it can initialize a null bodyweight for new selfweight actions. Historical UI editing remains disabled; durable operations may synchronize after midnight. Concurrent snapshot conflicts still require adopting cloud before reapplying. Today displays an update notice/command only when the safe candidate differs, checks account/date/revision across confirmation and clears stale active/rest/poster state through the existing renderer. This supersedes the blanket immutable-snapshot rule only for the explicit command; editing weekly/cycle templates alone never changes a started day.

Volume examples: 40*10*3=1200; 70*.65*12*3=1638. Test weeks/months/leap days, immutable snapshots, cancellations, zero volume, offline restart, idempotency, in-flight edits, conflict resolution, account isolation, server ownership and malformed inputs. Native DevTools verification and code package analysis supplement local source checks.
